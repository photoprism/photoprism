## OAuth Authorization Code Flow for Apps

**Last Updated:** October 21, 2026

Package `oauth` implements the protocol side of the OAuth 2.1 authorization code flow with PKCE that lets users connect apps and remote MCP clients to an instance. API handlers stay thin and call it; `internal/entity` provides the storage. The Portal's cluster OIDC provider is separate and keeps its own code.

### Building Blocks

| File             | Purpose                                                                                                                                                                                                                                                                                                                   |
|------------------|---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| `authorize.go`   | `ParseAuthorizeRequest`, `ValidateClient` (client ID and redirect URI, checked before an error may be redirected) and `Validate` (all other parameter bounds).                                                                                                                                                            |
| `pkce.go`        | `VerifyPKCE` and `ValidCodeChallenge`; only `S256` is accepted.                                                                                                                                                                                                                                                           |
| `redirect.go`    | `ValidRedirectURI`, `MatchRedirectURI` (exact match; any port for HTTP loopback URIs) and the response URL builders, which always add `iss` (RFC 9207).                                                                                                                                                                   |
| `client.go`      | `FindClient` returns an enabled, undeleted app client, read through the client cache, or a client metadata document `--oauth-apps` allows; `ClientOrigin` the origin shown on the consent page.                                                                                                                           |
| `metadata.go`    | `FindMetadataClient` fetches client metadata documents with `safe.Fetch` (no private addresses, no redirects, 16 KiB, 5 s) once the caller allows the fetch, `ParseClientMetadata` validates them, and a bounded cache keeps them for their `max-age` (5 minutes to 24 hours), longer while a document cannot be fetched. |
| `scope.go`       | `AppScopes` (`mcp` and the library resources MCP tools read), `ValidateScopes` (always adds `mcp`), `ScopeUsable`/`UsableScopes` (ACL rules per role; nothing is usable without `mcp`).                                                                                                                                   |
| `request.go`     | `NewRequest`, `FindRequest`, `CompleteRequest` (turns an approved request into a code once, valid for one minute) and `DenyRequest` for pending requests, valid for 15 minutes (`RequestTTL`).                                                                                                                            |
| `grant.go`       | `NewGrant`, `NewAccessToken` (one-hour sessions with the MCP endpoint as audience), `FindRefreshGrant` (the grant or the reason it cannot be used), `VerifyRefreshToken` and `RefreshGrant` (rotation; reuse revokes the grant), `RevokeRefreshToken` and `PurgeIdleGrants` (90 days without use).                        |
| `errors.go`      | OAuth error codes, `ErrInvalidGrant` with the reasons that wrap it (`ErrInvalidToken`, `ErrTokenExpired`, `ErrGrantNotFound`, `ErrRefreshTokenReused`), and `ErrSigningKey`.                                                                                                                                              |
| `code.go`        | `IssueCode`, `VerifyCode` and `RedeemCode` for single-use codes valid for one minute, and `PurgeExpired`, which the session cleanup worker calls.                                                                                                                                                                         |
| `client_form.go` | `ValidateClientForm`, `ValidateClientChange` and `ValidateRedirectURIs`, which the `clients add` and `clients mod` commands and the Pro client endpoints share: redirect URIs only on app clients, no secret, user or other role for them, and no switch to or from the app type.                                         |
| `secret.go`      | `HashSecret`, the SHA-256 hash under which codes, request IDs and refresh tokens are stored.                                                                                                                                                                                                                              |

### Rules

- `ValidateClient` checks syntax only. An error may be redirected to the client only after its redirect URI matched the client's registration (`MatchRedirectURI`); before that, it is rendered as a page.
- Redirect URIs match exactly as registered, without wildcards: a `*` in a registered URI is an ordinary character that matches only itself, never as a pattern. The one exception is the port of an HTTP loopback URI, which may differ (RFC 8252). Register each redirect URI an app uses separately.
- Redirect URIs are HTTPS URLs with a host, HTTP URLs on a loopback host (`localhost`, `127.0.0.0/8`, `::1`), or private-use schemes in reverse domain notation followed by a single slash (`app.example:/callback`, RFC 8252). Fragments and user info are refused. The response builders refuse any other URI and an empty issuer, keep the well-formed query parameters of the registered URI, and override `code`, `state`, `iss` and the error parameters, removing them when the response has no value for them.
- Repeated authorization request parameters are refused, and values must not contain control, format or line separator characters.
- A code is consumed by the first redemption attempt, even if the client, redirect URI or verifier do not match. A row without a user or resource is never redeemed.
- A pending request becomes a code only while it is unexpired (`entity.AuthCode.Replace`).
- Raw codes are returned to the client only; `auth_codes` stores their hash.
- Codes and refresh tokens carry an expiry and are signed with the instance signing key (`tokens.SignCode`, `tokens.SignRefresh`), each kind with its own purpose, so neither is accepted as the other. Codes expire after `CodeTTL`, refresh tokens `RefreshTokenTTL` after issue, which exceeds `GrantMaxIdle`. A value without a valid signature is refused with `ErrInvalidToken` and one past its expiry with `ErrTokenExpired` before anything is looked up (`VerifyCode`, `VerifyRefreshToken`, which the token endpoint calls before it resolves the client), and a refresh token whose grant is gone with `ErrGrantNotFound`; all three wrap `ErrInvalidGrant`. Clients treat both as opaque.
